# .kgg 格式与解密细节

这份笔记记录**实测结论**，目的是让将来酷狗改格式时能快速定位该改哪里。
下面所有数值都来自本目录那个真实样本（`鞠文娴 - 病变.kgg`，7,752,883 字节）。

---

## 一、.kgg 文件头（前 1024 字节，小端序）

| 偏移 | 长度 | 含义 | 实测值 |
|---|---|---|---|
| `0x00` | 16 | 固定 magic | `7C D5 32 EB 86 02 7F 4B A8 AF A6 8E 0F FF 99 14` |
| `0x10` | 4 | 头部总长度 | `1024` |
| `0x14` | 4 | 加密版本 | `5`（3 = 旧版，未实现） |
| `0x18` | 4 | 保留 | `FF FF FF FF` |
| `0x44` | 4 | keyId 长度 | `32` |
| `0x48` | N | **keyId**（UTF-8） | `2d1616df1a9732cd989d275e00b96007` |
| `0x68` | 4 | 码率字符串长度 | `3` |
| `0x6C` | 3 | 码率字符串 | `"320"` |
| `0x6F` | 16 | 标识哈希（见下文"坑"） | `106b03419140c6f92f4fe525b9aa3f4a` |
| `0x400` | … | 加密音频载荷 | 全长 = 文件大小 − 1024 |

**载荷长度自洽性**：`7752883 − 1024 = 7751859`，与密钥库 `DownloadItem.FileSize` 完全一致。
这条恒等式是判断"头部长度是否解析正确"最快的办法。

## 二、密钥从哪来：KGMusicV3.db

位置：`%APPDATA%\KuGou8\KGMusicV3.db`（约 38 MB）。

### 2.1 数据库本身也是加密的

它是**按 1024 字节分页**做 AES-128-CBC 加密的 SQLite：

```
pageKey(n) = MD5(masterKey ‖ LE32(n) ‖ LE32(0x546c4173))
pageIv(n)  = MD5( 由 LCG 生成的 4 个 LE32 )
masterKey  = 1d613145b247bf7f3d189672144fe4bf
```

LCG 递推（32 位有符号空间，对应 `pageIv`）：

```
value = seed * 0x9ef4 − floor(seed / 0xce26) * 0x7fffff07
若最高位为 1，则 value += 0x7fffff07
```

**第 1 页的特殊处理**：密文 `16..24` 字节是 `8..16` 字节的拷贝，解密前先搬运过去，
解密后再比对，用来验证主密钥是否正确。解密完成后把 `0..16` 字节替换成标准
`"SQLite format 3\0"` 头。其余页直接用页号解密整页。

判定"这是加密库"的特征：`offset 20` 处 u32 == `0x20204000`，且
`pageSize = (byte16 << 8) | (byte17 << 16)` 是 2 的幂。

### 2.2 密钥记录（有**两个**来源，两个都要读）

#### 来源一：`DownloadItem`（常规下载）

可用密钥就是 `EnKey` 非空的行：

| 字段 | 作用 |
|---|---|
| `EnHash` | 等于 .kgg 头部的 keyId，用来精确命中 |
| `EnKey` | 加密的音频密钥（Base64 文本） |
| `MD5` / `FileSize` | 文件标识与**明文长度**（长度可用于校验，MD5 不能，见下） |
| `SongName` / `Artist` / `Album` | 用于写 ID3 标签 |
| `BitRate` / `EncryptionType` | 元信息 |

#### 来源二：`ShareFileItems`（另一条下载通道）

一部分加密歌曲的密钥**不记在 DownloadItem 里**，只记在这张表：

| 字段 | 作用 |
|---|---|
| `EncryptionKeyId` | 就是 keyId，等于 .kgg 头部的那个 |
| `EncryptionKey` | 加密的音频密钥，与 `EnKey` **格式完全相同**（704 字符 Base64、`EncryptionVersion=5`） |
| `FileName` | 本地文件全路径，歌名/歌手只能从这里推 |
| `MD5` / `FileSize` / `BitRate` / `Quality` | 元信息 |

> ⚠️ **这是踩过的坑**：早期实现只读 `DownloadItem`，结果
> `华晨宇、G.E.M. 邓紫棋 - 光年之外 (Live).kgg` 一直报"密钥库里没有这首歌的密钥"，
> 而它的密钥其实好好地在 `ShareFileItems` 里。**只读一张表会漏歌，而且报错信息看起来
> 像是"你没在本机下载"**，非常容易误判。

实测（2026-09-11）：`DownloadItem` 11 条、`ShareFileItems` 10 条，去重后 **12 条**
（9~10 条重叠，各有一两条独有）。两表都读之后，本机 9 个 `.kgg` 全部命中。

**密钥是下载时写入的，不需要先播放这首歌。** 实测：

- 本机所有 `.kgg` 都能下载完直接转换，包括从未播放过的；
- 刚下载、从未播放过的歌同样一次成功；
- `StartTime` / `CompleteTime` / `AccessTime` 这些时间字段在库里是空值或无效值，**不能**用来判断"密钥何时写入"。

> ⚠️ 网上（包括 kgg-dec 的 README）常见"必须至少播放一次才能解密"的排错提示。
> 在本项目的实测环境里**不成立**：密钥随下载响应一起落库。
> 那条提示可能来自 Android 端或缓存试听等其它场景。
> 找不到密钥时，真实原因更可能是：**密钥在另一张表里（见上）**、不是在本机下载的、或下载没完成。

### 2.3 EnKey 解包

1. Base64 解码。
2. 若结果以 `QQMusic EncV2,Key:` 开头：剥前缀 → 两次 Tencent-TEA 解密（两把固定密钥）→ 再 Base64 解码一次。
3. **deriveV1**：用固定 8 字节 `69 56 46 38 2B 20 15 0B` 与原始密钥前 8 字节交替组成 TEA 密钥，
   对第 8 字节之后的部分做 Tencent-TEA 解密，再拼回前 8 字节 → **音频密钥**。

Tencent-TEA = 标准 TEA 解密 + CBC 式链式异或 + 7 字节零填充校验。
**实现要点**：中间量必须按 64 位语义算（Kotlin 的 `Long`），最后才 `and 0xffffffff`。
如果按 32 位逐次截断，结果会错。本项目用 `BigInt` 精确复现。

本样本的解包结果：EnKey 704 字符 → Base64 得 528 字节 → **音频密钥 512 字节**。

## 三、音频流解密（QMC2）

按**音频密钥长度**分流：

| 密钥长度 | 实现 | 说明 |
|---|---|---|
| ≤ 300 字节 | `MapCipher` | 由 `(偏移²+71214) % 密钥长度` 取字节位置，再做一个 8 位循环左移后异或 |
| > 300 字节 | `Rc4Cipher` | 5120 字节分段 + 段间跳过的 RC4 式流密码 |

本样本走 **Rc4Cipher**（512 字节密钥）。
`Rc4Cipher` 的关键细节：每段都从 KSA 之后的 **S 盒副本**重新开始，
`skip = (offset % 5120) + segmentSkip(offset / 5120)`；前 128 字节走单独分支。
`segmentSkip` 依赖一个"密钥非零字节连乘"的哈希值，且它自身在乘法溢出回绕时要 break —— 这点容易写错。

## 四、⚠️ 一个必须记住的坑：MD5 字段不是明文 MD5

第一版实现里我假设头部 `0x6F` 的 16 字节（与密钥库 `DownloadItem.MD5` 相同）是明文音频的 MD5，
用它做完整性断言。**这是错的**，实测数据：

| 计算对象 | MD5 |
|---|---|
| 整个 `.kgg` 文件 | `01d4a9c706a3119689563bc4fab9504a` |
| `.kgg` 去掉 1024 字节头部 | `2d1616df1a9732cd989d275e00b96007` ← **等于 keyId** |
| **我们解出的明文音频** | `21bdc58c05c6d631781670319c8d9c58` |
| 头部 `0x6F` / 密钥库 `MD5` | `106b03419140c6f92f4fe525b9aa3f4a` ← **以上都不是** |

结论：
- `EnHash`(keyId) = **MD5(加密载荷)**，是文件标识；
- 头部 `0x6F` / 库里的 `MD5` 是**另一个文件标识哈希**（可能是服务端原始文件的哈希，
  酷狗每次重新下载会重写 Ogg 页序号与 CRC，所以哈希会变）；
- **两者都不能用来断言明文完整性。**

### 因此现在的校验策略是结构性的

1. **明文长度**必须等于密钥库 `FileSize`；
2. 明文是 Ogg 时，**逐页校验 Ogg CRC32**（容器自带强校验，1752 页全过才算通过；
   概率上等价于逐页 MD5）；
3. 容器标识嗅探（`ID3`/帧同步 → mp3，`fLaC` → flac，`OggS` → ogg，`RIFF` → wav）；
4. 转码后校验编解码器、时长（±1.5s）、码率（±8%），可选整片解码校验。

**任何一项不通过就删除产物**，绝不在 `output\` 里留下坏文件。

## 五、已知限制

| 限制 | 说明 |
|---|---|
| 只实现 KGG **v5** | 头部版本 3 的旧文件会明确报错 |
| `MapCipher` 分支（短密钥）**未经真实样本验证** | 本样本只有 512 字节长密钥，走的是 Rc4Cipher；短密钥分支是照规格实现的，尚未遇到实物 |
| 密钥库格式可能随酷狗升级变化 | 若 `page1 完整性校验失败`，说明主密钥或分页算法变了 |
| 依赖本机环境 | 换设备解不开是设计使然，不是 bug |

## 六、算法出处与许可

`.kgg` 的解密规格来自公开实现，本项目是据规格的独立实现（常量与规格一致）：

- [unlock-music · kgg-dec](https://git.unlock-music.dev/um/kgg-dec) —— 原始 C++ 解密工具，格式由它逆向公开
- [OpenConverter](https://github.com/nowa277/OpenConverter)（**Apache-2.0**）—— 含 `src/decoders/kgg/` 的
  JS 移植与 `KggDatabaseCipher`，本项目的密钥库解密与 QMC2 规格参照了它
- [iyuu/kgm-decoder-python](https://github.com/jieyideshijie/kgm-decoder-python) —— KGM 家族的 Python 参考

Apache-2.0 允许本项目照规格实现并注明出处；此处即注明。
